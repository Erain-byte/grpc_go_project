# Keycloak 本地安装与配置指南

本文记录当前项目可重复执行的 Keycloak 配置。运行参数以 `deploy/identity/README.md` 和 Compose 文件为准。

## 1. 启动

先启动 Docker Desktop，确认 `docker version` 同时显示 Client 和 Server。然后执行：

```powershell
cd D:\grpc_go_project\deploy\identity
docker compose --env-file ..\postgres\.env -f ..\postgres\compose.yaml up -d
docker compose config --quiet
docker compose up -d
docker compose ps
```

管理台：`http://localhost:8180/admin/`。首次账号来自 `.env` 的 `KEYCLOAK_ADMIN` 与 `KEYCLOAK_ADMIN_PASSWORD`。

## 2. 创建永久管理员

Compose 的 Bootstrap 管理员只用于初始化。进入 `master` Realm：

1. 创建用户 `kc-admin`。
2. 在 Credentials 中设置密码并关闭 `Temporary`。
3. 在 Role mapping 中分配 `realm-management` Client 的 `realm-admin`。
4. 使用无痕窗口验证 `kc-admin` 能登录管理台。
5. 生产环境停用临时管理员并轮换 Bootstrap 凭据。

本地出现黄色临时管理员提示可以暂时保留，生产必须处理。

## 3. 创建项目 Realm

左上角 Realm 菜单选择 **Create realm**，名称填写 `grpc-project` 并启用。

Realm 是用户、角色、Client、Session 和签名密钥的隔离边界。`master` 用于管理 Keycloak；业务用户与 Client 放在 `grpc-project`。页面中的 **Current realm** 只是说明当前选择，实际 Realm 名称显示为 `grpc-project`。

生产环境也需要 Realm，但应使用导入模板或自动化创建，避免重复手工配置。

Discovery 地址：

```text
http://localhost:8180/realms/grpc-project/.well-known/openid-configuration
```

## 4. Realm Roles

进入 **Realm roles** 创建：

| Role | 用途 |
|---|---|
| `user` | 普通业务用户 |
| `admin` | 管理后台用户 |
| `super-admin` | 系统超级管理员 |

这些是 `grpc-project` 的业务角色，不要创建在 `master` Realm。

## 5. Clients

### 5.1 grpc-api

创建 OpenID Connect Client `grpc-api`，表示受保护的后端 API Audience。它不负责浏览器跳转。

### 5.2 user-web

创建 confidential Client `user-web`：

- Standard flow：开启
- Direct access grants：关闭
- Valid redirect URI：`http://localhost:4180/oauth2/callback`
- Valid post logout redirect URI：`http://localhost:4180/*`
- Web origins：本地 BFF 不需要时留空

### 5.3 admin-web

创建 confidential Client `admin-web`：

- Standard flow：开启
- Direct access grants：关闭
- Valid redirect URI：`http://localhost:4181/oauth2/callback`
- Valid post logout redirect URI：`http://localhost:4181/*`

Root URL 与 Home URL 当前可以留空。回调端口对应后续两套 OAuth2 Proxy，不是 Keycloak 自己的端口。

生产环境必须把 localhost 回调改为实际 HTTPS 域名，并同步修改 OAuth2 Proxy；不一致会出现 `invalid_redirect_uri` 或回调失败。

### 5.4 user-app（Expo Web / iOS）

`user-app` 是 Expo 用户端使用的 OpenID Connect 公共客户端，不保存 Client Secret：

- Client authentication：关闭
- Authorization：关闭
- Standard flow：开启
- Direct access grants：关闭
- Implicit flow：关闭
- Require PKCE：开启
- PKCE Method：`S256`
- Require DPoP bound tokens：当前关闭

本机开发地址：

```text
Root URL:                       http://localhost:8081
Home URL:                       http://localhost:8081
Valid redirect URI:             http://localhost:8081/oauth/callback
Valid post logout redirect URI: http://localhost:8081/*
Web origin:                     http://localhost:8081
Native redirect URI:            web3-user://oauth/callback
Native post logout URI:         web3-user://*
```

Expo Web 当前使用 `8081`，不是 `8100`。Gateway HTTP 使用 `9080`，Keycloak 使用 `8180`。

## 6. Audience Mapper

进入 **Client scopes → Create client scope**：

- Name：`grpc-api-audience`
- Protocol：OpenID Connect
- Type：None
- Include in token scope：On
- Include in OpenID Provider Metadata：Off

保存后进入该 Scope 的 **Mappers → Add mapper → By configuration → Audience**：

- Name：`grpc-api-audience`
- Included Client Audience：留空
- Included Custom Audience：`grpc-api`
- Add to ID token：Off
- Add to access token：On
- Add to lightweight access token：On
- Add to token introspection：On

分别进入 `user-web`、`admin-web` 和 `user-app` 的 **Client scopes**，点击 **Add client scope**，选择 `grpc-api-audience`，Assigned type 设为 **Default**。

## 7. 测试用户

在 `grpc-project` Realm 创建：

- `user-test`：密码 Temporary=Off，Realm Role 分配 `user`
- `admin-test`：密码 Temporary=Off，Realm Role 分配 `admin`

模拟或实际登录后检查 Access Token：

```json
{
  "iss": "http://localhost:8180/realms/grpc-project",
  "aud": ["grpc-api", "account"],
  "azp": "user-web",
  "realm_access": {"roles": ["user"]}
}
```

Admin Token 的 `azp` 应为 `admin-web`，角色应包含 `admin`。若 `aud` 只有 `account`，说明 Audience Mapper 未填写 Custom Audience，或 Scope 未作为 Default 绑定。

## 8. Expo 用户端地址与环境切换

### 8.1 本机浏览器开发

| 组件 | 地址 |
|---|---|
| Expo Web | `http://localhost:8081` |
| Gateway HTTP | `http://localhost:9080` |
| Keycloak | `http://localhost:8180` |
| Keycloak Issuer | `http://localhost:8180/realms/grpc-project` |

前端只向 Gateway 请求业务接口；Keycloak 负责登录、Token 获取、刷新和退出。

### 8.2 手机真机开发

手机中的 `localhost` 指向手机自身，而不是开发电脑。真机访问电脑服务时，应使用电脑局域网 IP，例如：

```text
Gateway: http://192.168.1.10:9080
Issuer:  http://192.168.1.10:8180/realms/grpc-project
```

电脑防火墙需要允许相应端口。原生 App 优先使用 `web3-user://oauth/callback`；如果通过手机浏览器调试 Web 版本，还要把实际 Web 地址加入 Keycloak 的 Valid redirect URIs 和 Web origins。

### 8.3 生产环境

生产环境必须使用 HTTPS 正式域名，例如：

```text
用户前端: https://app.example.com
Gateway:  https://api.example.com
Keycloak: https://auth.example.com
Issuer:   https://auth.example.com/realms/grpc-project
```

`user-app` 需要增加：

```text
Valid redirect URI:             https://app.example.com/oauth/callback
Valid post logout redirect URI: https://app.example.com/*
Web origin:                     https://app.example.com
```

`web3-user://oauth/callback` 可以继续用于原生 App；后续也可以升级为 Universal Links/App Links。

### 8.4 Expo 环境变量

Keycloak 和 Gateway 地址不能写死在业务代码中，应按环境注入：

```env
# 本机开发
EXPO_PUBLIC_KEYCLOAK_ISSUER=http://localhost:8180/realms/grpc-project
EXPO_PUBLIC_GATEWAY_URL=http://localhost:9080

# 生产示例
EXPO_PUBLIC_KEYCLOAK_ISSUER=https://auth.example.com/realms/grpc-project
EXPO_PUBLIC_GATEWAY_URL=https://api.example.com
```

生产发布时必须同步修改：前端环境变量、Keycloak 外部域名与反向代理、Client 回调地址及 Web Origin。Gateway 的业务 API 路径不需要改变。

### 8.5 Token 存储安全约束

- iOS/Android：Access Token、Refresh Token 和 ID Token 使用系统 SecureStore 保存。
- Web：所有 Token 只保存在页面内存中，不写入 `localStorage` 或 `sessionStorage`。
- Web 页面刷新后允许重新建立登录状态；Keycloak SSO Session 尚未失效时，重新授权通常不要求再次输入密码。
- 生产 Web 若要求无感刷新与长期会话，应采用 BFF，由服务端管理 Refresh Token，浏览器只持有 `HttpOnly + Secure + SameSite` Session Cookie。
- PKCE 保护授权码交换过程，但不能防止 XSS 读取浏览器 JavaScript 可访问的 Token，因此不能用 PKCE 代替安全存储方案。

### 8.6 用户注册与人机验证

Expo 不接收或保存用户密码。登录和注册表单均由 Keycloak 托管：

1. 在 `Realm settings → Login` 开启 `User registration`。
2. Expo 登录使用标准 Authorization Code + PKCE 请求。
3. Expo 注册在相同 OIDC 请求中增加 `prompt=create`，直接进入 Keycloak 注册页。
4. 在 `Authentication → Flows → Registration` 中把 `reCAPTCHA` 设置为 `Required`。
5. 打开 reCAPTCHA 的配置，填写 Site Key 和 Secret；开发 Key 必须允许 `localhost`，生产 Key 只允许正式认证域名。
6. 根据所申请的 Key 类型选择 v2 可见挑战或 v3 分数验证。
7. 同时开启 Keycloak 的 Brute Force Detection，防护密码登录爆破；注册验证码不能替代登录失败锁定策略。

reCAPTCHA Secret 只能保存在 Keycloak 配置或外部密钥系统中，不能写入前端、Git 或本文档。导出 Realm 后必须检查并脱敏验证码 Secret。

Keycloak 26.7 内置 reCAPTCHA 主要保护注册流程。若要求登录页也在特定条件下展示验证码，需要实现或安装 Keycloak Authenticator SPI，并把它加入 Browser Flow；不能在 Expo 中增加一个可被绕过的普通验证接口。

## 9. 导出与恢复

项目保留两类文件：

- `grpc-project-realm.json`：原始导出，只留本机，可能包含 Secret。
- `grpc-project-realm.template.json`：脱敏模板，可提交并由 Compose 导入。

模板至少保留 Realm、Roles、Clients、Client Scope 和 Audience Mapper；删除测试用户、Session、真实 Secret 和本机专用配置。Client Secret 通过 Compose 环境变量注入。

`--import-realm` 只在 Realm 不存在时导入，不覆盖已有 Realm。生产首次部署应在空的生产数据库中导入模板，然后配置正式域名并验证 Token。
