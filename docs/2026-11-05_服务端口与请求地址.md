# 服务端口与请求地址

更新时间：2026-11-05

本文以当前开发环境配置、Gateway 路由和 `deploy` 目录中的 Docker Compose 为准。生产环境应通过域名、HTTPS、内网 DNS 或负载均衡访问，不应直接照搬本文的本机地址。

## 1. 访问原则

客户端正常情况下只访问 Gateway，不直接请求 Admin、User、LLM 或 Web3：

```text
浏览器 / APP / API 客户端
        |
        | HTTP + Keycloak Access Token
        v
Gateway :9080
        |
        | gRPC + authorization metadata + Trace Context
        +----------> Admin :9082
        +----------> User  :9084 ----------> Web3 :9086
        +----------> LLM   :9083
                         User/Admin 也可调用 LLM :9083
```

- `0.0.0.0` 是服务监听地址，不能作为客户端请求地址。
- 本机开发请求应使用 `127.0.0.1` 或 `localhost`。
- Consul 中保存的是服务发现地址，调用方应优先通过服务名发现实例，不要在业务代码中硬编码端口。
- pprof、数据库、Redis、RabbitMQ、Consul 和 Jaeger 都不是对外业务 API。

## 2. 业务服务端口总表

| 服务 | 协议 | 当前监听地址 | 本机访问地址 | Consul 服务名 | 用途 |
| --- | --- | --- | --- | --- | --- |
| Gateway HTTP | HTTP | `0.0.0.0:9080` | `http://127.0.0.1:9080` | `gateway-service` | 唯一对外业务入口 |
| Gateway gRPC | gRPC | `0.0.0.0:9081` | `127.0.0.1:9081` | `gateway-service` | Gateway gRPC 转发入口及健康检查 |
| Admin | gRPC/mTLS | `127.0.0.1:9082` | `127.0.0.1:9082` | `admin-service` | 管理员、用户管理和 LLM 转发 |
| LLM | gRPC | `0.0.0.0:9083` | `127.0.0.1:9083` | `llm-service` | 对话、流式对话、模型调用和历史记录 |
| User | gRPC | `0.0.0.0:9084` | `127.0.0.1:9084` | `user-service` | 用户资料、初始化、LLM/Web3 转发 |
| 预留 | - | - | `9085` 当前未使用 | - | 为后续服务保留，不是现有入口 |
| Web3 | gRPC | `0.0.0.0:9086` | `127.0.0.1:9086` | `web3-service` | 钱包、余额、交易和 TRON 授权体检 |

说明：Gateway、User、LLM、Web3 的 `0.0.0.0` 仅表示监听所有 IPv4 网卡。它们注册到 Consul 的开发地址为 `127.0.0.1`。

## 3. 外部 HTTP 请求入口

### 3.1 基础地址

| 使用场景 | 基础地址 | 说明 |
| --- | --- | --- |
| API/APP 携带 Bearer Token 直连 Gateway | `http://127.0.0.1:9080` | 当前本地开发入口 |
| 用户浏览器经 OAuth2 Proxy | `http://127.0.0.1:4180` | 登录后代理到 Gateway `9080` |
| 管理后台经 OAuth2 Proxy | `http://127.0.0.1:4181` | 仅允许 `admin`、`super-admin`，代理到 Gateway `9080` |

启用 Gateway HTTP TLS 后，应把基础地址改为 `https://<域名>`，业务路径保持不变。

## 4. OAuth2 Proxy 与 Keycloak 地址

### 4.1 OAuth2 Proxy

| 组件 | 地址 | 回调地址 | 上游 |
| --- | --- | --- | --- |
| User OAuth2 Proxy | `http://127.0.0.1:4180` | `http://localhost:4180/oauth2/callback` | `http://host.docker.internal:9080` |
| Admin OAuth2 Proxy | `http://127.0.0.1:4181` | `http://localhost:4181/oauth2/callback` | `http://host.docker.internal:9080` |

### 4.2 Keycloak

| 用途 | 地址 |
| --- | --- |
| Keycloak 控制台/用户入口 | `http://127.0.0.1:8180` |
| Realm Issuer | `http://localhost:8180/realms/grpc-project` |
| OIDC Discovery | `http://localhost:8180/realms/grpc-project/.well-known/openid-configuration` |
| 登录授权 | `http://localhost:8180/realms/grpc-project/protocol/openid-connect/auth` |
| Token 获取/刷新 | `http://localhost:8180/realms/grpc-project/protocol/openid-connect/token` |
| JWKS 公钥 | `http://localhost:8180/realms/grpc-project/protocol/openid-connect/certs` |
| 登出 | `http://localhost:8180/realms/grpc-project/protocol/openid-connect/logout` |
| Keycloak 管理/健康端口 | `http://127.0.0.1:9000` |

容器内部的 OAuth2 Proxy 使用 `http://keycloak:8080` 请求 Token 和 JWKS；这是 Docker 网络地址，宿主机不要使用它。

## 8. 当前需要注意的配置问题

### 8.1 Admin 与 Docker Consul 探活地址

Admin 当前监听：

```text
127.0.0.1:9082
```

Consul 配置的探活地址：

```text
host.docker.internal:9082
```

Docker 容器访问 `host.docker.internal` 时通常无法访问只绑定到宿主机回环网卡的服务。因此需要实际验证 Admin 的 Consul 健康检查；如果不通，可采用以下方案之一：

1. 开发环境把 Admin `host` 改为 `0.0.0.0`，同时依靠防火墙和 mTLS 限制访问；
2. 让 Consul Agent 与 Admin 运行在相同网络命名空间；
3. 使用能够被 Consul 容器访问的指定宿主机网卡地址。

不要把 `127.0.0.1` 直接替换成公网监听地址后关闭 mTLS。

### 8.2 本机地址与容器地址不能混用

```text
宿主机访问 Redis：127.0.0.1:6379
容器访问 Redis：  redis:6379

宿主机访问 Keycloak：http://localhost:8180
容器访问 Keycloak：  http://keycloak:8080
```

请求失败时应先确认调用方运行在宿主机还是 Docker 网络中。

## 9. 快速检查命令

```powershell
# Gateway 健康检查
Invoke-RestMethod http://127.0.0.1:9080/health

# 查看监听端口
Get-NetTCPConnection -State Listen |
    Where-Object LocalPort -In 4180,4181,6060,6061,6062,6063,9080,9081,9082,9083,9084,9086 |
    Sort-Object LocalPort

# 查看 Consul 服务
Invoke-RestMethod http://127.0.0.1:8500/v1/agent/services

# 查看 Jaeger
Start-Process http://127.0.0.1:16686
```
