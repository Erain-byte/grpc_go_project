# 服务部署与 Keycloak 配置指南

本文档以当前仓库代码为准，说明本地联调、生产部署时需要启动的组件、必须修改的配置，以及 Keycloak、OAuth2 Proxy、mTLS、Consul KV 和数据库迁移之间的关系。服务职责、调用链和代码分层见 [服务架构与目录结构说明](./2026-11-11_服务架构与目录结构说明.md)。

> 安全原则：`.env`、数据库密码、Client Secret、Cookie Secret、API Key、TLS 私钥不得提交 Git。仓库内只提交 `.env.example`、证书生成程序和不含秘密的配置模板。

## 1. 系统调用关系

```text
用户浏览器（Expo Web :8081）
    ├─ 公开钱包体检 ───────────────→ Gateway :9080
    └─ OIDC + PKCE 登录 ───────────→ Keycloak :8180

管理浏览器（Vue :3000）
    └─ OAuth2 Proxy :4181 ─────────→ Gateway :9080

Gateway :9080
    ├─ gRPC/mTLS → Admin :9082
    └─ gRPC/mTLS → User  :9084
                         └─ gRPC/mTLS → Web3 :9086

所有 Go 服务 ── OTLP gRPC → Jaeger :4317
所有服务 ────── 注册/发现 → Consul :8500
```

公开钱包体检不要求登录；收藏地址、用户资料和其他私有操作仍要求 Access Token。

## 3. 部署前准备

### 3.1 软件

- Docker Desktop 与 Docker Compose v2；
- Go（版本以各模块 `go.mod` 为准）；
- Node.js 与 npm；
- PowerShell；
- 生产环境还需要 HTTPS 反向代理、DNS 和 Secret Manager。

### 3.2 创建本地环境文件

在项目根目录执行：

```powershell
Copy-Item deploy/postgres-admin/.env.example deploy/postgres-admin/.env
Copy-Item deploy/postgres-user/.env.example deploy/postgres-user/.env
Copy-Item deploy/postgres-web3/.env.example deploy/postgres-web3/.env
Copy-Item deploy/postgres-llm/.env.example deploy/postgres-llm/.env
Copy-Item deploy/postgres-keycloak/.env.example deploy/postgres-keycloak/.env
Copy-Item deploy/redis/.env.example deploy/redis/.env
Copy-Item deploy/rabbitmq/.env.example deploy/rabbitmq/.env
Copy-Item deploy/identity/.env.example deploy/identity/.env
Copy-Item deploy/oauth2-proxy/.env.example deploy/oauth2-proxy/.env
```

随后修改所有 `change-me`。以下值必须保持一致：

- `deploy/postgres-admin/.env` 的 `ADMIN_DB_PASSWORD` = 启动 Admin 时的 `ADMIN_DB_PASSWORD`；
- User、Web3 数据库密码同理；
- `deploy/postgres-keycloak/.env` 与 `deploy/identity/.env` 的 `KEYCLOAK_DB_PASSWORD` 相同；
- `deploy/redis/.env`、`deploy/oauth2-proxy/.env` 和启用 Redis 的 Go 服务使用同一 Redis 密码；
- `USER_WEB_CLIENT_SECRET`、`ADMIN_WEB_CLIENT_SECRET` 必须与 Keycloak 对应 Client 的 Secret 相同。

Cookie Secret 应分别随机生成，User 与 Admin 不得共用。可使用：

```powershell
[Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(32))
```

### 3.3 创建 Docker 外部网络和卷

当前 Compose 文件使用了外部网络/卷，首次部署先执行：

```powershell
docker network create grpc-go-identity
docker network create grpc-go-admin-database
docker network create grpc-go-user-database
docker network create grpc-go-web3-database
docker network create grpc-go-llm-database

docker volume create identity_keycloak-postgres-data
docker volume create grpc-go-admin-postgres-data
docker volume create grpc-go-user-postgres-data
docker volume create grpc-go-web3-postgres-data
docker volume create grpc-go-llm-postgres-data
docker volume create observability_consul_data
docker volume create observability_rabbitmq_data
```

`grpc-go-shared` 和 Redis 数据卷会由 Redis Compose 创建。重复创建已存在的网络或卷不会影响数据。

## 4. 生成本地 mTLS 证书

在项目根目录执行：

```powershell
go run ./scripts/generate-mtls
```

生成目录为 `certs/mtls`，该目录不应被 Git 跟踪。关键文件：

```text
certs/mtls/ca/ca.crt
certs/mtls/gateway/service.crt
certs/mtls/gateway/service.key
certs/mtls/admin/service.crt
certs/mtls/admin/service.key
certs/mtls/user/service.crt
certs/mtls/user/service.key
certs/mtls/web3/server.crt
certs/mtls/web3/server.key
certs/mtls/consul/client.crt
certs/mtls/consul/client.key
```

证书 SAN 与 Consul 服务名必须匹配：

| 服务 | Consul 服务名 / TLS ServerName | 证书 SAN |
| --- | --- | --- |
| Gateway | `gateway-service` | `gateway-service` |
| Admin | `admin-service` | `admin-service` |
| User | `user-service` | `user-service` |
| Web3 | `web3-service` | `web3-service` |

同一服务扩容为多个实例时，实例共用服务身份，例如 `user-service`；不要用 `user1`、`user2` 作为不同 ServerName。生产环境应由内部 CA、Vault PKI 或云证书系统签发和轮换，不能使用开发脚本生成的 CA 私钥。

Windows 路径目前写在四个 YAML 中。更换项目目录或部署到 Linux 时，必须修改 `ca_file`、`cert_file`、`key_file` 和 `client_ca_file`。

## 6. Keycloak 配置（重点）

### 6.1 Realm 与 Issuer

- Realm：`grpc-project`；
- 本地 Issuer：`http://localhost:8180/realms/grpc-project`；
- 生产 Issuer 示例：`https://auth.example.com/realms/grpc-project`。

本地 `deploy/identity/compose.yaml` 中必须保留：

```yaml
KC_HOSTNAME: http://localhost:8180
```

它决定 Token 的 `iss`。虽然 OAuth2 Proxy 容器使用 `http://keycloak:8080` 兑换 Token 和读取 JWKS，但签发出来的 `iss` 仍必须是浏览器和 Go 服务共同认识的外部地址。不要把本地 Issuer 改成容器名，否则宿主机上的 Gateway、User、Admin、Web3 无法按同一 Issuer 校验。

### 6.2 Realm 角色

至少创建三个 Realm Role：

- `user`：普通用户；
- `admin`：后台管理员；
- `super-admin`：超级管理员。

用户账号必须分配正确角色。OAuth2 Proxy 和 Go 中间件都会校验角色，角色错误会返回 403，而不是登录失败。

### 6.3 `grpc-api` Audience

创建 Client Scope：`grpc-api-audience`，增加 Audience Mapper：

- Mapper type：Audience；
- Included Client Audience：`grpc-api`；
- Add to access token：On。

把此 Scope 以 `Default` 方式绑定到 `user-web`、`admin-web`、`user-app`。最终 Access Token 必须包含：

```json
{
  "iss": "http://localhost:8180/realms/grpc-project",
  "aud": ["grpc-api"],
  "realm_access": { "roles": ["user"] }
}
```

项目中的 Go 服务按 RS256 签名、Issuer、Audience、有效期和角色共同校验 Token。

### 6.4 Client 配置表

#### `grpc-api`

表示受保护的后端 API Audience，不用于浏览器登录：

- Client authentication：Off；
- Standard Flow：Off；
- Direct Access Grants：Off。

#### `user-app`（Expo Web / iOS）

这是公共客户端，不能保存 Client Secret：

- Client authentication：Off；
- Standard Flow：On；
- Direct Access Grants：Off；
- Implicit Flow：Off；
- Require PKCE：On；
- PKCE Method：`S256`。

本地回调和来源：

```text
Valid redirect URIs:
http://localhost:8081/oauth/callback
web3-user://oauth/callback

Valid post logout redirect URIs:
http://localhost:8081/*
web3-user://*

Web origins:
http://localhost:8081
```

生产 Web 地址必须替换为正式 HTTPS 域名；iOS/Android 保留应用自己的受控 Deep Link 或 Universal Link。

#### `user-web`（OAuth2 Proxy 用户入口）

- Client authentication：On；
- Standard Flow：On；
- Direct Access Grants：Off；
- Valid redirect URI：`http://localhost:4180/oauth2/callback`；
- Valid post logout URI：`http://localhost:4180/*`；
- Default Client Scope：`grpc-api-audience`。

Client Secret 同时写入：

- `deploy/identity/.env` 的 `USER_WEB_CLIENT_SECRET`；
- `deploy/oauth2-proxy/.env` 的 `USER_WEB_CLIENT_SECRET`。

#### `admin-web`（管理端 OAuth2 Proxy）

- Client authentication：On；
- Standard Flow：On；
- Direct Access Grants：Off；
- Valid redirect URI：`http://localhost:4181/oauth2/callback`；
- Valid post logout URI：`http://localhost:4181/*`；
- Default Client Scope：`grpc-api-audience`。

Client Secret 同时写入 Identity 和 OAuth2 Proxy 的 `.env`。Admin Proxy 只允许 `admin`、`super-admin` 角色。

#### `admin-management`（Admin 服务调用 Keycloak Admin API）

此 Client 只在“后台创建/禁用用户，需要同时修改 Keycloak”时启用：

- Client authentication：On；
- Service account roles：On；
- Standard Flow：Off；
- Direct Access Grants：Off；
- Service Account 仅授予 `realm-management` 下的：
  - `manage-users`；
  - `query-users`；
  - `view-realm`。

然后设置：

```powershell
$env:ADMIN_KEYCLOAK_CLIENT_SECRET = "从 Keycloak Credentials 复制的 Secret"
```

并将 `admin/etc/admin.yaml` 中 `auth.management.enabled` 改为 `true`。当前为 `false` 时，Admin 不会调用 Keycloak 管理 API。

### 6.5 Realm 导入的行为

`deploy/identity/realm/grpc-project-realm.template.json` 只在数据库中不存在 `grpc-project` Realm 时导入。修改模板后重启 Keycloak，不会覆盖已经存在的 Realm。

已有环境应在管理控制台手工修改，或导出、审核后重新导入；不要为了重新导入模板直接删除生产 Keycloak 数据卷。

### 6.6 启动 OAuth2 Proxy

Keycloak、Redis 和 Gateway 都可用后执行：

```powershell
docker compose --env-file deploy/oauth2-proxy/.env -f deploy/oauth2-proxy/compose.yaml config --quiet
docker compose --env-file deploy/oauth2-proxy/.env -f deploy/oauth2-proxy/compose.yaml up -d
```

本地地址：

- User Proxy：`http://localhost:4180`；
- Admin Proxy：`http://localhost:4181`。

Admin 前端的 `VITE_ADMIN_BFF_URL` 应为 `http://localhost:4181`。OAuth2 Proxy 将 Access Token 注入转发请求，Gateway 仍会独立验证签名、Issuer、Audience、有效期和角色。

## 7. 写入 Consul KV

Gateway 和 Admin 当前要求启动时读取有效的运行时配置，缺失会拒绝启动：

```powershell
Get-Content .\deploy\consul\kv\global-runtime.json -Raw |
    docker exec -i grpc-go-consul consul kv put grpc-go/config/global/runtime -

Get-Content .\deploy\consul\kv\gateway-runtime.json -Raw |
    docker exec -i grpc-go-consul consul kv put grpc-go/config/gateway/runtime -

Get-Content .\deploy\consul\kv\admin-runtime.json -Raw |
    docker exec -i grpc-go-consul consul kv put grpc-go/config/admin/runtime -
```

验证：

```powershell
docker exec grpc-go-consul consul kv get grpc-go/config/gateway/runtime
docker exec grpc-go-consul consul kv get grpc-go/config/admin/runtime
```

KV 文件不得存放密码、Token、API Key 或私钥。生产 CORS 必须把 localhost 来源替换为真实前端域名。

## 8. 每个服务需要修改的配置

修改配置时遵循以下规则：

- 地址、端口、开关和非敏感参数写入 YAML；
- 密码、Token、Client Secret、HMAC Key、上游 API Key 通过环境变量或 Secret Manager 注入；
- `name`、Consul 服务名、TLS `server_name` 和证书 SAN 是一组关联配置，不能只修改其中一个；
- `0.0.0.0` 只能作为监听地址，不能作为 Consul 注册地址；
- `127.0.0.1` 只适用于服务运行在同一台主机的本地环境。

### 8.1 Gateway：`gateway/etc/gateway.yaml`

Gateway 是公网 HTTP 入口，也是调用 Admin、User 等内部服务的 gRPC 客户端。

#### 部署时必须检查

| 字段 | 本地值 | 生产修改要求 |
| --- | --- | --- |
| `environment` | `development` | 改为 `production`，也可用 `GATEWAY_ENVIRONMENT` 覆盖 |
| `host` | `0.0.0.0` | 容器内通常仍为 `0.0.0.0` |
| `advertise_host` | `127.0.0.1` | 改为其他服务和 Consul 能访问的内网 IP 或 DNS 名 |
| `port` | `9080` | 按部署端口修改；反向代理上游必须同步 |
| `grpc_port` | `9081` | 修改后同步 Consul、防火墙和调用方 |
| `auth.access_token.issuers` | localhost Keycloak | 改为正式 Keycloak HTTPS Issuer，必须与 Token `iss` 完全一致 |
| `auth.access_token.jwks_url` | localhost JWKS | 改为正式 Keycloak JWKS 地址 |
| `auth.access_token.audience` | `grpc-api` | 一般不改；若修改，Keycloak Audience Mapper 和所有服务必须同步 |
| `redis.host`、`redis.port` | 本机 Redis | 改为生产 Redis 地址；集群模式填写 `cluster_addresses` |
| `consul.host`、`consul.port` | 本机 Consul | 推荐指向同机 Consul Client Agent |
| `consul.check_host` | `host.docker.internal` | 改为 Consul Agent 能访问 Gateway 的地址 |
| `tracing.endpoint` | `127.0.0.1:4317` | 改为生产 OTel Collector/Jaeger OTLP 地址 |

必须注入：

```powershell
$env:GATEWAY_ENVIRONMENT = "production"
$env:GATEWAY_REDIS_PASSWORD = "从 Secret Manager 读取"
$env:GATEWAY_ANTI_REPLAY_SECRET = "独立的高强度随机值"
```

#### TLS 配置

`grpc_server` 是 Gateway 的入站 gRPC TLS；`grpc` 是 Gateway 调用内部服务的出站 mTLS，两者不要混淆：

```yaml
grpc_server:
  use_tls: true
  tls_server_name: "gateway-service"
  cert_file: "/run/secrets/mtls/gateway/service.crt"
  key_file: "/run/secrets/mtls/gateway/service.key"
  client_ca_file: "/run/secrets/mtls/ca/ca.crt"

grpc:
  use_tls: true
  cert_file: "/run/secrets/mtls/gateway/service.crt"
  key_file: "/run/secrets/mtls/gateway/service.key"
  ca_file: "/run/secrets/mtls/ca/ca.crt"
```

`grpc.plaintext_services` 当前包含 `llm-service`，表示 LLM 是迁移期明文例外。LLM 接入 mTLS 后必须删除该项。

#### HTTP TLS、CORS 和运行时配置

- 如果 HTTPS 在 Nginx/Ingress/负载均衡器终止，`http.tls.enabled` 保持 `false`；
- 如果 Gateway 自己直接提供 HTTPS，设为 `true` 并配置公网证书和私钥；
- `http.tls.health_check_skip_verify` 生产必须为 `false`；
- CORS、限流等运行时参数来自 Consul KV `grpc-go/config/gateway/runtime`，不是只改 YAML；
- `runtime_config_required: true` 表示 KV 缺失或非法时 Gateway 拒绝启动；
- `service.public_apis` 只表示公开 API 规则，HTTP 路由仍在 `internal/server/routes_*.go` 注册，不能通过 YAML 新增路由。

#### pprof、日志和 Trace

- `pprof.host` 保持 `127.0.0.1`，或放在独立管理网络；
- 不要在公网设置 `allow_remote: true`；
- `logger.filename` 要指向有写权限并已挂载的持久目录；
- 生产 Trace 不建议 `const + 1.0` 全采样，应按容量改为概率采样；
- OTel 使用 TLS 时补齐 `tracing.ca_file/cert_file/key_file/server_name`。

### 8.2 Admin：`admin/etc/admin.yaml`

Admin 负责后台业务、管理员资料、操作日志，并可选择通过 Service Account 管理 Keycloak 用户。

#### 部署时必须检查

| 字段 | 本地值 | 生产修改要求 |
| --- | --- | --- |
| `environment` | `development` | 改为 `production` |
| `host` | `127.0.0.1` | 跨主机或容器部署时改为可监听地址，例如 `0.0.0.0` |
| `grpc_port` | `9082` | 修改后同步 Consul、证书和调用方 |
| `database.host/port` | `127.0.0.1:5433` | 改为 Admin PostgreSQL 内网地址 |
| `database.username/dbname` | `admin_service/admin` | 必须与数据库创建参数一致 |
| `database.ssl_mode` | `disable` | 生产数据库支持 TLS 时改为 `require`、`verify-ca` 或 `verify-full` |
| `redis.host/port` | 本机 Redis | 改为生产 Redis；启用 ACL/TLS 时同步客户端能力 |
| `rabbitmq.host/port` | 本机 RabbitMQ | 改为生产 AMQP 地址 |
| `auth.access_token.*` | localhost Keycloak | 改为生产 Issuer 和 JWKS |
| `consul.check_host` | `host.docker.internal` | 改为 Consul 能访问 Admin 的地址 |
| `tracing.endpoint` | 本机 Jaeger | 改为生产 Collector |

必须或按启用功能注入：

```powershell
$env:ADMIN_ENVIRONMENT = "production"
$env:ADMIN_DB_PASSWORD = "从 Secret Manager 读取"
$env:ADMIN_REDIS_PASSWORD = "从 Secret Manager 读取"
$env:ADMIN_RABBITMQ_PASSWORD = "从 Secret Manager 读取"
$env:ADMIN_CONSUL_TOKEN = "启用 Consul ACL 时设置"
$env:ADMIN_KEYCLOAK_CLIENT_SECRET = "启用 Keycloak 管理功能时设置"
```

#### Keycloak 管理功能

默认配置：

```yaml
auth:
  management:
    enabled: false
```

只有完成第 6.4 节的 `admin-management` Service Account 和最小权限授权后，才能改为 `true`。同时修改：

- `base_url`：生产 Keycloak 基础地址，不含 Realm 路径；
- `realm`：通常保持 `grpc-project`；
- `client_id`：通常保持 `admin-management`；
- `ADMIN_KEYCLOAK_CLIENT_SECRET`：只能通过环境变量注入。

如果保持 `false`，后台新增本地管理员记录不会自动得到可登录的 Keycloak 账号，部署验收时必须明确这一点。

#### 数据库、RabbitMQ 与限流

- `read_write_split_enabled: false` 时所有读写走主库；启用后必须填写真实只读副本 `replica_addresses`；
- RabbitMQ 当前承载管理员操作日志，若 `enabled: true`，RabbitMQ 密码和交换机/队列必须准备好；
- 不要随意改已有环境的 exchange、routing key、queue 名称，否则可能形成两套消息拓扑；
- `rate_limit` 使用 Redis，`redis_timeout`、窗口和限额按压测结果调整；
- Admin 的动态配置来自 `grpc-go/config/admin/runtime`，当前 `runtime_config_required: true`。

#### gRPC/mTLS

`grpc.cert_file/key_file` 同时用于 Admin 入站和 Admin 调用其他服务。生产路径需改为 Secret 挂载路径；`tls_server_name`、Consul 服务名和证书 SAN 都应保持 `admin-service`。`plaintext_services` 中的 LLM 例外应在 LLM 接入 TLS 后移除。

### 8.3 User：`user/etc/user.yaml`

User 负责用户资料、分表路由，并作为 Gateway/Admin 到 Web3 的业务转发层。

#### 部署时必须检查

| 字段 | 本地值 | 生产修改要求 |
| --- | --- | --- |
| `environment` | `development` | 改为 `production` |
| `host` | `0.0.0.0` | 容器内通常不改 |
| `advertise_host` | `127.0.0.1` | 改为其他服务能访问的内网地址 |
| `grpc_port` | `9084` | 修改后同步 Consul、证书和调用方 |
| `id_generator.node_id` | `1` | 生产通过 `USER_SNOWFLAKE_NODE_ID` 覆盖，每个并行实例唯一 |
| `database.host/port` | `127.0.0.1:5434` | 改为 User PostgreSQL 内网地址 |
| `auth.access_token.*` | localhost Keycloak | 改为生产 Issuer 和 JWKS |
| `consul.check_host` | `host.docker.internal` | 改为 Consul Agent 能检查 User 的地址 |
| `tracing.endpoint` | 本机 Jaeger | 改为生产 Collector |

环境变量：

```powershell
$env:USER_ENVIRONMENT = "production"
$env:USER_DB_PASSWORD = "从 Secret Manager 读取"
$env:USER_CONSUL_TOKEN = "启用 Consul ACL 时设置"
$env:USER_SNOWFLAKE_NODE_ID = "每个实例唯一的数字"
$env:USER_REDIS_PASSWORD = "启用 Redis 后设置"
$env:USER_RABBITMQ_PASSWORD = "启用 RabbitMQ 后设置"
```

#### 分表配置不可随意修改

```yaml
database:
  sharding:
    enabled: true
    table_count: 8
    table_prefix: "users_"
```

已有数据后，不能直接把 `table_count` 从 8 改为 16，也不能修改 `table_prefix`，否则相同用户 ID 会被路由到不同物理表。扩容分表必须设计数据迁移、双写/停写和回滚方案。

#### Redis、RabbitMQ 和限流

- 当前 `redis.enabled: false`，只有业务代码实际依赖缓存或分布式状态时再开启；
- 当前 `rabbitmq.enabled: false`，启用前要确认消费者、重试队列和死信队列已经部署；
- `rate_limit` 是单实例本地令牌桶，不是集群总限流；
- 多实例总入口限流仍由 Gateway 的分布式策略承担；
- 生产需要本地保护时，将 `rate_limit.enabled` 改为 `true` 并通过压测确定速率和并发数。

#### Consul 与 mTLS

- `runtime_config_required: false` 表示 User 可在没有动态 KV 时启动；生产决定依赖动态配置后再设为 `true`；
- `registration_maintenance` 用于注册丢失后的补注册，通常保持启用；
- `deregister_on_shutdown: true` 用于优雅退出时注销实例；
- `grpc.tls_server_name`、服务名和证书 SAN 保持 `user-service`；
- `grpc.max_recv_message_size` 和 `max_send_message_size` 当前为 4 MiB，确有大消息需求时才提高，优先使用流式传输。

### 8.4 Web3：`web3/etc/web3.yaml`

Web3 负责钱包绑定、Nonce、链上只读查询、交易索引和 TRON USDT 授权体检。

#### 部署时必须检查

| 字段 | 本地值 | 生产修改要求 |
| --- | --- | --- |
| `environment` | `development` | 改为 `production` |
| `advertise_host` | `127.0.0.1` | 改为 User/Consul 能访问的内网地址 |
| `grpc_port` | `9086` | 修改后同步 Consul、证书和 User |
| `database.host/port` | `127.0.0.1:5436` | 改为 Web3 PostgreSQL 内网地址 |
| `redis.host/port` | 本机 Redis | 改为生产 Redis；Web3 当前要求 Redis 健康 |
| `auth.access_token.*` | localhost Keycloak | 改为生产 Issuer 和 JWKS |
| `wallet_signature.domain` | `localhost` | 改为正式产品域名 |
| `wallet_signature.uri` | `http://localhost` | 改为正式 HTTPS URI |
| `consul.check_host` | `host.docker.internal` | 改为 Consul 能访问 Web3 的地址 |
| `tracing.endpoint` | 本机 Jaeger | 改为生产 Collector |

环境变量：

```powershell
$env:WEB3_ENVIRONMENT = "production"
$env:WEB3_DB_PASSWORD = "从 Secret Manager 读取"
$env:WEB3_REDIS_PASSWORD = "从 Secret Manager 读取"
$env:WEB3_CONSUL_TOKEN = "启用 Consul ACL 时设置"
$env:WEB3_TRON_API_KEY = "当前实现使用的上游 Key"
$env:WEB3_TRON_USAGE_HMAC_KEY = "独立高强度随机值"
$env:WEB3_RABBITMQ_PASSWORD = "启用 RabbitMQ 后设置"
```

#### 钱包签名

`wallet_signature.domain`、`uri` 和前端显示/发起签名时使用的内容必须一致，否则签名验证会失败。生产使用 HTTPS 域名，`nonce_ttl` 通常保持较短时间，Nonce 必须在 Redis 中一次性消费。不要通过配置关闭地址、签名或 Nonce 校验。

#### EVM 链与扫描器

- `blockchain.chains[].chain_id` 必须与目标链一致；
- `rpc_urls` 中含 API Key 时，应由环境变量或 Secret 模板生成，不应提交 Git；
- `scanner.enabled` 默认关闭；启用前必须确认起始区块、确认数、批量大小、数据库幂等和重组处理；
- 多 Web3 实例同时扫描时必须依赖 Redis 分布式锁，防止重复扫描。

#### TRON 授权体检

当前 `tron_approvals.enabled: false`，因此页面显示 `TRON approval query is not enabled` 属于预期行为。启用前必须确认：

1. TRONSCAN 与 TronGrid 上游可访问；
2. API Key、日调用量和预算已准备；
3. `usdt_contract` 是目标网络的官方 USDT 合约；
4. `daily_*_limit`、`max_pages`、`max_spenders` 和 `verify_workers` 已按套餐及压测设置；
5. 缓存不会让用户误认为结果是实时链上最终状态。

当前代码把一个 `WEB3_TRON_API_KEY` 同时赋给 TRONSCAN 与 TronGrid。两家服务的 Key 通常不能通用；正式启用前应将代码拆分为 `WEB3_TRONSCAN_API_KEY` 和 `WEB3_TRONGRID_API_KEY`。未拆分时不能拿一个平台的 Key 冒充另一个平台的 Key。

#### Product 公共配置

`product` 下的字段会由 `GetPublicWeb3Config` 返回给匿名客户端，因此只能放可公开内容：

- `favorite_limit`：本地收藏上限；
- `minimum_refresh_interval`：客户端最短刷新间隔；
- `support_email`、`feedback_url`、`testflight_url`：正式发布前填写；
- `privacy_policy_version`：发布隐私政策时同步更新；
- `maintenance_message`：维护提示，不得包含内部错误或秘密。

`product` 中绝不能放 TRON API Key、数据库地址、内部服务地址或任何 Secret。

#### RabbitMQ、限流和 TLS

- `rabbitmq.enabled` 当前为 `false`，启用前部署下游消费者和死信处理；
- `rate_limit` 是 Web3 单实例保护，Gateway 仍负责外部统一限流；
- `redis.health_required: true` 表示 Redis 不可用时启动/健康状态会受影响；
- `grpc.tls_server_name`、Consul 服务名和证书 SAN 保持 `web3-service`；
- Web3 当前证书文件名是 `server.crt/server.key`，与其他服务的 `service.crt/service.key` 不同，挂载时不要写错。

### 8.5 LLM：`llm/config/llm.yaml`

LLM 是 Python 服务，当前默认使用 `mock` Provider，尚不是生产真实模型服务。部署前检查：

| 字段 | 当前值 | 修改要求 |
| --- | --- | --- |
| `environment` | `development` | 生产改为 `production` |
| `host` | `0.0.0.0` | 容器内可保留 |
| `advertise_host` | `127.0.0.1` | 改为调用方可访问的内网地址 |
| `grpc_port` | `9083` | 修改后同步发现和调用方 |
| `grpc.use_tls` | `false` | 接入内部 mTLS 后改为 `true` 并配置证书 |
| `auth.access_token.*` | localhost Keycloak | 改为生产 Issuer/JWKS |
| `model.provider` | `mock` | 接入真实 Provider 后修改，并通过 Secret 注入其 API Key |
| `consul.address` | `127.0.0.1:8500` | 改为生产 Consul Agent |
| `tracing.endpoint` | 本机 Jaeger | 改为生产 Collector |

Consul ACL Token 通过 `LLM_CONSUL_TOKEN` 注入。当前 Gateway、Admin、User 将 `llm-service` 列为明文例外；完成 LLM mTLS 后必须同步移除这些 `plaintext_services`。

注意：当前 LLM 配置中的 `service_name: llm-service` 与 Consul 注册名 `llm-service-grpc` 含义不同。正式联调前必须确认调用方实际发现的是哪一个名称并统一，不能只靠猜测修改。

| 类型 | Gateway | Admin | User | Web3 | LLM |

任何服务从本机迁移到容器、虚拟机或 Kubernetes 后，至少同时检查：监听地址、注册地址、健康检查地址、依赖地址、证书挂载路径、证书 SAN、防火墙和反向代理配置。

## 12. 本地验收清单

1. Keycloak discovery 的 `issuer` 为 `http://localhost:8180/realms/grpc-project`；
2. User Web 能打开公开钱包体检页面，未登录也能调用公开体检接口；
3. `user-app` 使用 Authorization Code + PKCE S256 登录；
4. Access Token 含 `aud=grpc-api` 和正确 Realm Role；
5. 普通用户不能进入 Admin Proxy，管理员可以；
6. Admin 退出后 OAuth2 Proxy Cookie 和 Keycloak SSO 会话都失效；
7. Consul 中四个 Go 服务健康；
8. Jaeger 能看到 `Gateway → User → Web3 → TRON` Trace；
9. pprof 仅本机或管理网络可访问；
10. PostgreSQL 数据写入对应独立数据库；
11. TRON 授权查询未配置真实上游 Key 时应明确返回“未启用”，而不是伪造成功结果。

## 13. 生产环境必须修改

### 13.1 Keycloak

- 使用 `deploy/identity/compose.prod.yaml` 的 `start`，禁止 `start-dev`；
- `KEYCLOAK_HOSTNAME` 设置为正式域名，例如 `auth.example.com`；
- 由反向代理提供 HTTPS，并正确传递受信任的 `X-Forwarded-*` 头；
- 所有 Client 的 Redirect URI、Post Logout URI、Web Origin 改为精确 HTTPS 地址；
- 创建永久管理员、启用 MFA，删除临时 bootstrap 管理员；
- 缩短高权限 Token 生命周期，配置登录失败保护和审计事件；
- 定期备份 Keycloak PostgreSQL 和 Realm 导出文件；
- Client Secret 轮换后同步更新 OAuth2 Proxy/服务 Secret，并滚动重启。

### 13.2 OAuth2 Proxy

- `COOKIE_SECURE=true`；
- Cookie 名使用 `__Host-` 前缀；
- Issuer、登录、兑换、JWKS 地址统一使用正式 HTTPS 域名并恢复标准 OIDC Discovery；
- 白名单只允许正式前端域名；
- Redis 使用 TLS 或可信私网；
- Secret 通过 Docker Secret、Kubernetes Secret、Vault 或云 Secret Manager 注入。

### 13.3 网络与数据

- PostgreSQL、Redis、RabbitMQ、Consul、Jaeger、pprof、gRPC 端口不得直接暴露公网；
- 公网只开放 HTTPS 反向代理入口；
- 服务间启用 mTLS，CA 私钥离线或交给 PKI 系统管理；
- 数据库启用自动备份、恢复演练和最小权限账号；
- CORS 不使用 `*`，只允许实际 Web 域名；
- TRON API Key 和预算 HMAC Key 放入 Secret Manager；
- 为上游 TRON API 设置超时、重试、熔断、预算和告警。

## 14. 常见故障

### 登录后 403

依次检查 Realm Role、`grpc-api-audience` 是否为 Default Scope，以及 Token 中的 `aud`、`realm_access.roles`。

### OAuth2 Proxy 回调 500

检查 Client Secret 是否一致、Redis 是否可用、Keycloak Issuer 是否仍为 `http://localhost:8180/...`，并查看：

```powershell
docker compose --env-file deploy/oauth2-proxy/.env -f deploy/oauth2-proxy/compose.yaml logs --tail=200
```

### 修改 Realm 模板后没有变化

Realm 已存在，`--import-realm` 不会覆盖。应在控制台修改或执行受控的导入流程。

### Gateway/Admin 启动失败并提示运行配置缺失

重新写入第 7 节的 Consul KV，并确认 Key 名与 YAML 中 `runtime_config_key` 一致。

### gRPC TLS 提示证书名称不匹配

检查 `tls_server_name`、Consul 服务名和证书 SAN 是否一致；再检查客户端加载的 CA 是否为签发该服务证书的 CA。

### TRON approval query is not enabled

这是 `web3/etc/web3.yaml` 中 `tron_approvals.enabled: false` 或上游 Key 未配置时的预期结果。配置独立的 TRONSCAN/TronGrid Key 并完成代码拆分后再启用。

## 15. 发布与回滚建议

1. 先备份数据库和 Keycloak；
2. 执行迁移任务；
3. 滚动发布 Web3、User、Admin；
4. 发布 Gateway；
5. 发布 OAuth2 Proxy 和前端；
6. 执行登录、公开体检、管理端、Trace 和数据库冒烟测试；
7. 出现异常时回滚应用版本；数据库迁移必须准备单独的向前修复方案，不依赖直接删除数据。
