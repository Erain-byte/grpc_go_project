# 服务架构与目录结构说明

本文档说明当前项目的服务边界、请求流转、代码分层、数据归属和阅读顺序。部署、端口和生产配置见 [服务部署与 Keycloak 配置指南](./2026-11-11_服务部署与Keycloak配置指南.md)。

## 1. 项目定位

当前项目采用“公网 HTTP Gateway + 内部 gRPC 微服务”的结构：

- 浏览器和 App 只访问 Gateway 或 Keycloak，不直接访问内部 gRPC 服务；
- Gateway 将 HTTP 请求转换为 protobuf 请求，并通过 Consul 发现内部服务；
- Admin、User、Web3、LLM 按业务领域拆分；
- Keycloak 负责身份认证和 Token 签发；
- 各 Go 服务仍会独立校验原始 Access Token；
- 服务间使用 gRPC，Go 服务逐步统一使用 mTLS；
- PostgreSQL 按服务独立，禁止跨服务直接查询其他服务数据库。

## 2. 总体架构

```text
┌──────────────────────────── 客户端 ────────────────────────────┐
│ Expo Web / iOS                         Vue Admin Web           │
│ :8081                                  :3000                   │
└──────────────┬────────────────────────────┬────────────────────┘
               │ OIDC + PKCE               │ OAuth2 Proxy Session
               ▼                            ▼
         Keycloak :8180              Admin OAuth2 Proxy :4181
               │                            │ 注入 Access Token
               └──────────────┬─────────────┘
                              ▼
                     Gateway HTTP :9080
                  路由、鉴权、限流、协议转换
                     │          │          │
              gRPC/mTLS   gRPC/mTLS   gRPC（迁移中）
                     │          │          │
                     ▼          ▼          ▼
                  Admin       User        LLM
                  :9082       :9084       :9083
                     │          │
                     │          └──── gRPC/mTLS ────→ Web3 :9086
                     │                                  │
                     └──── Admin → User → Web3          ├─ TRONSCAN
                                                        ├─ TronGrid
                                                        └─ EVM RPC
```

基础设施：

```text
Consul       服务注册、发现、健康检查、运行时配置
Redis        Session、Nonce、缓存、限流或短期状态
RabbitMQ     操作日志和后续异步领域事件
PostgreSQL   每个服务独立持久化
Jaeger/OTel  分布式链路追踪
pprof        Go 服务性能诊断
```

## 3. 四条主要请求链路

### 3.1 匿名钱包体检

```text
User Web
  → Gateway 公开 HTTP 路由
  → UserService 的公开 RPC
  → User Forwarder
  → Web3Service
  → TRONSCAN / TronGrid
  → 原路返回结果
```

当前公开入口包括：

- `GET /v1/web3/config`；
- `POST /v1/web3/events`；
- `POST /v1/web3/feedback`；
- `POST /v1/tron/usdt/approvals/check`；
- `POST /v1/airdrops/check`。

这条链路不要求 Keycloak 登录，但仍经过 Gateway IP 限流。公开仅代表“不需要用户身份”，不代表可以绕过地址校验、上游预算、超时、日志和风控。

为什么仍经过 User：当前对外协议统一挂在 `UserService` 上，Gateway 只需要发现 User，User 再负责把 Web3 请求转发给 Web3 服务。这样保持了既定的 `Gateway → User → Web3` 边界。

### 3.2 已登录用户请求

```text
User Web / iOS
  → Keycloak Authorization Code + PKCE
  → 获得 Access Token
  → Gateway HTTP Authorization: Bearer <token>
  → Gateway 校验 JWT
  → User gRPC metadata.authorization
  → User 再次校验 JWT
  → Web3 gRPC metadata.authorization（需要身份的方法）
  → Web3 再次校验 JWT
```

用户钱包绑定、钱包列表、余额和交易等接口位于 `/user/web3/*` 保护路由下。收藏公开地址属于前端本地能力；涉及用户账户的服务端数据必须登录。

### 3.3 管理端请求

```text
Admin Web :3000
  → Admin OAuth2 Proxy :4181
  → Keycloak 登录并检查 admin/super-admin
  → OAuth2 Proxy 注入 Access Token
  → Gateway /admin/*
  → AdminService
     ├─ 管理员业务 → Admin PostgreSQL
     ├─ 用户查询   → UserService → User PostgreSQL
     ├─ Web3 管理  → UserService → Web3Service
     └─ AI 对话    → LLMService
```

Admin 不应直接连接 User 或 Web3 数据库。管理端查询其他领域时，必须通过对应服务的 RPC，以保留权限、审计和业务规则。

### 3.4 LLM 请求

当前存在三类调用入口：

- Gateway `/llm/*` 直接转发到 LLM；
- User 的 Chat/StreamChat 转发到 LLM；
- Admin 的 Chat/StreamChat 转发到 LLM。

LLM 当前默认使用 `mock` Provider，目录结构已经为真实 Provider、会话存储、RAG 和 MCP 预留边界，但不应把这些预留目录视为已完成的生产能力。

## 4. 服务职责与边界

### 4.1 Gateway

职责：

- 提供 HTTP 和 gRPC 入口；
- 注册公开、用户、管理端和 LLM 路由；
- JWT 初次校验和角色检查；
- CORS、分布式限流、Request ID、错误转换；
- HTTP/JSON 与 protobuf/gRPC 适配；
- 从 Consul 发现下游并复用 gRPC 连接；
- 传播 Authorization、Request ID 和 Trace Context。

不负责：

- 保存用户、管理员或钱包业务数据；
- 实现 Web3 链上规则；
- 替 Keycloak签发业务 Token；
- 直接访问其他服务数据库。

### 4.2 Admin

职责：

- 管理员资料、角色、权限和操作日志；
- 管理端用户查询的业务编排；
- 管理端 Web3 运行状态、调用量和反馈查询；
- 可选调用 Keycloak Admin API 创建或禁用登录账号；
- 通过 RabbitMQ 异步记录操作日志。

Admin 自己拥有：

- 管理员表；
- 角色和权限表；
- 操作日志表。

Admin 不拥有普通用户和链上钱包数据。

### 4.3 User

职责：

- 根据 Keycloak `sub` 初始化和查询本地用户；
- 用户总索引与 8 张用户分表路由；
- 用户分组、成员关系及当前已有的用户资金领域模型；
- 向 Web3、LLM 转发用户侧请求；
- 保持用户领域与外部身份系统的映射。

`UserIdentityIndex` 是用户全局索引，用于由 Keycloak Subject 或其他唯一身份定位用户及分表；真正用户数据写入 `users_00` 至 `users_07`。

### 4.4 Web3

职责：

- 非托管钱包地址绑定；
- 生成并一次性消费签名 Nonce；
- 验证钱包签名与地址归属；
- 查询支持链、余额和交易；
- 维护本地交易快照、扫描游标和幂等事件；
- TRON USDT 授权体检；
- 记录上游调用量、客户端事件和用户反馈。

Web3 不保存用户私钥，不代替用户签名，不提供托管提现。链上钱包地址与 User 用户 ID 建立关联，但钱包领域数据归 Web3 数据库所有。

### 4.5 LLM

职责边界：

- 提供普通对话和流式对话 gRPC；
- 隔离模型 Provider；
- 后续承载会话、RAG、MCP 和模型调用治理。

当前状态：

- Python + `grpc.aio`；
- 配置模型和 Consul 注册已建立；
- 默认 `mock` Provider；
- 真实模型、数据库、Redis、完整可观测性仍需继续实现和验收。

## 5. 数据归属

| 数据 | 所属服务 | 存储位置 | 其他服务访问方式 |
| --- | --- | --- | --- |
| Keycloak 用户、密码、会话 | Keycloak | Keycloak PostgreSQL | OIDC/Admin API |
| 管理员、角色、权限 | Admin | Admin PostgreSQL | Admin RPC |
| 管理操作日志 | Admin | Admin PostgreSQL/RabbitMQ | Admin RPC |
| 用户总索引、用户资料 | User | User PostgreSQL | User RPC |
| 用户分组与成员 | User | User PostgreSQL | User RPC |
| 钱包绑定 | Web3 | Web3 PostgreSQL | Web3 RPC，经 User 暴露 |
| 链上交易快照、扫描游标 | Web3 | Web3 PostgreSQL | Web3 RPC |
| Nonce、扫描锁、短期缓存 | Web3 | Redis | 仅 Web3 内部 |
| OAuth2 Proxy Session | OAuth2 Proxy | Redis | 仅 Proxy 使用 |
| 动态限流/CORS | Gateway/Admin | Consul KV | 各自 Manager 热更新 |

禁止通过数据库 JOIN 跨越服务边界。例如 Admin 查询用户列表应调用 UserService，而不是连接 User PostgreSQL。

## 6. Proto 与接口边界

### 6.1 Proto 目录

```text
proto/
├─ common/v1/    公共鉴权扩展等协议
├─ gateway/v1/   Gateway gRPC 协议
├─ admin/v1/     AdminService
├─ user/v1/      UserService
├─ web3/v1/      Web3Service 和 Web3 消息
└─ llm/v1/       LlmService
```

Proto 是服务间契约，不是业务实现。修改 `.proto` 后需要重新生成代码、发布 Proto 模块版本，并更新 Admin、Gateway、User、Web3 的模块引用。

### 6.2 为什么 User Proto 中有 Web3 方法

当前公开调用路径要求 `Gateway → User → Web3`，所以 `UserService` 引用了 `web3.v1` 请求和响应，并定义相应转发 RPC。User Handler 不从 User 数据库查询链上数据，而是调用 `user/internal/forwarder/web3.go`。

### 6.3 为什么 Admin Proto 也有 User/Web3 方法

AdminService 是管理端面向 Gateway 的契约。它通过 Admin Forwarder 调用 User；User 再调用 Web3。Admin Proto 暴露的是“管理端允许执行的能力”，并不表示 Admin 拥有这些数据。

### 6.4 AuthRule

`proto/common/v1/security.proto` 提供方法级 `AuthRule`：

- `public: true`：允许匿名调用；
- `roles`：限制 Realm Role；
- 未声明规则的方法默认保护。

Gateway HTTP 路由仍要正确放入公开组或 JWT 中间件组。Proto 声明和 Gateway 路由必须同时审查，不能只改其中一个。

## 7. Go 服务通用目录分层

Admin、User、Web3 基本遵循下列分层：

```text
cmd/<service>/main.go
    ↓
internal/app/app.go
    ↓ 创建依赖
internal/config
internal/logger / tracer
internal/databases / redis / mq / consul
internal/svc/servicecontext.go
    ↓ 注入 Server 和业务层
internal/server
    ↓ 注册 gRPC Handler 和中间件
internal/handler
    ↓ 协议转换
internal/service
    ↓ 业务编排
internal/repository
    ↓ 数据访问
internal/model
```

辅助层：

- `internal/forwarder`：调用其他服务；
- `internal/grpc` 或 `grpcclient`：服务发现、连接复用、TLS；
- `internal/middleware`：鉴权、Request ID、恢复、错误、限流、Trace；
- `internal/runtimeconfig`：Consul KV 快照与热更新；
- `internal/sharding`：只负责确定物理表，不承载业务规则；
- `pkg/apperror`：跨层的应用错误和 gRPC 状态转换。

### 7.1 `app` 层

`app.Run` 是组合根，负责：

1. 加载和校验配置；
2. 初始化日志和 Trace；
3. 创建并检查数据库、Redis、RabbitMQ、Consul；
4. 创建 ClientManager 和 ServiceContext；
5. 创建 gRPC/HTTP/pprof Server；
6. 注册 Consul；
7. 等待退出信号或 Server 异常；
8. 按依赖关系优雅关闭。

业务逻辑不应写入 `app.go`。

### 7.2 `svc.ServiceContext`

ServiceContext 是依赖容器，不是全局单例。它保存配置、数据库客户端、Redis、Router、ID Generator、ClientManager、Logger 等已经构造完成的对象，再注入 Handler、Service 和 Repository。

新增依赖的正确顺序：

```text
config 增加配置
→ app 创建并检查依赖
→ ServiceContext 保存接口或客户端
→ 业务层通过 ServiceContext/构造函数使用
→ app 负责关闭
```

### 7.3 `server` 层

负责监听端口、注册 gRPC 服务、安排拦截器顺序和健康检查。典型注册：

```go
userv1.RegisterUserServiceServer(grpcServer, handler.NewUserHandler(svcCtx))
```

它把生成代码中的 `UserServiceServer` 接口与项目 Handler 关联起来。不要在 Server 中写数据库操作。

### 7.4 `handler` 层

负责：

- 接收 protobuf 请求；
- 获取 Context 身份；
- 做轻量参数适配；
- 调用 Service 或 Forwarder；
- 返回 protobuf 响应和统一错误。

Handler 不应直接拼复杂 SQL，也不应实现链上算法。

### 7.5 `service` 层

负责完整业务用例。例如钱包绑定 Service 会编排：

```text
读取身份 → 校验地址 → 消费 Nonce → 验证签名 → 检查重复绑定
→ Repository 事务写入 → 返回结果
```

业务一致性、权限语义和事务边界主要放在这一层。

### 7.6 `repository` 和 `model`

- Model 描述持久化结构；
- Repository 封装查询、锁、分页和事务；
- Service 不应散落 GORM 查询；
- Repository 不决定“用户是否有权执行某项业务”。

### 7.7 `forwarder` 与 gRPC ClientManager

Forwarder 知道调用哪个 protobuf Client 和 RPC；ClientManager 负责：

- 从 Consul 获取健康实例；
- 建立并复用 `grpc.ClientConn`；
- 选择负载均衡策略；
- 加载客户端证书和验证目标 SAN；
- 关闭或更新连接。

`factory func(grpc.ClientConnInterface) T` 将共享连接转换为具体的生成客户端，例如 `web3v1.NewWeb3ServiceClient(conn)`。

### 13.1 User：Expo


## 14. 身份、Request ID 和 Trace 的传播

### 14.1 身份

```text
HTTP Authorization Header
→ Gateway JWT Middleware
→ gRPC metadata: authorization
→ User/Admin JWT Interceptor
→ 下游 OutgoingContext
→ Web3/LLM
```

只传播白名单 metadata，不复制所有客户端 Header。目前主要传播：

- `authorization`；
- Request ID；
- OpenTelemetry Trace Context（由 OTel gRPC Handler 注入/提取）。

### 14.2 Request ID

入口已有 Request ID 就沿用，没有则由中间件生成。日志、错误响应和下游调用应使用同一个 ID，方便在没有完整 Trace 时排查一次请求。

### 14.3 Trace

调用链目标：

```text
Gateway HTTP Span
→ Gateway gRPC Client Span
→ User/Admin Server Span
→ 下游 Client Span
→ Web3/LLM Server Span
→ TRON HTTP Client Span
```

业务层需要手工 Span 时，应从当前 `context.Context` 创建，不能使用 `context.Background()` 切断父链路。

## 15. 错误处理原则

- Repository 返回底层错误或已分类错误；
- Service 增加业务语义；
- Handler 转成统一 gRPC Status；
- Gateway 转成稳定 HTTP 状态和响应结构；
- 日志记录内部原因，客户端响应不泄露 SQL、路径、Token、私钥或上游 Key；
- panic recovery 是最后防线，不能代替正常错误处理；
- `InvalidArgument`、`Unauthenticated`、`PermissionDenied`、`NotFound`、`Conflict`、`ResourceExhausted`、`Unavailable` 应保持语义一致。

## 16. 新增功能的标准步骤

以新增一个用户侧 Web3 接口为例：

1. 明确数据归属和调用链；
2. 在 `proto/web3/v1/web3.proto` 增加 Web3 RPC；
3. 如果必须经过 User，在 `proto/user/v1/user.proto` 增加同类型转发 RPC；
4. 为方法声明正确的 AuthRule；
5. 重新生成 Proto 并更新模块版本；
6. Web3 增加 Handler → Service → Repository/上游 Client；
7. User 增加 Handler 和 Web3 Forwarder；
8. Gateway 增加 Forwarder 方法和 HTTP 路由；
9. 明确路由是匿名、普通用户还是管理员；
10. 增加单元测试、集成测试和错误用例；
11. 补充配置、监控、限流、Trace 和部署文档；
12. 完成 Gateway → User → Web3 联调。

如果只是 User 自有数据，不应为了形式强行经过 Web3；如果是 Web3 数据，也不应把查询实现到 User Repository。

## 17. 推荐阅读顺序

第一次阅读整个项目：

1. `docs/2026-11-11_服务架构与目录结构说明.md`；
2. `proto/*/v1/*.proto`；
3. `gateway/internal/server/routes_*.go`；
4. `gateway/internal/forwarder/*.go`；
5. 目标服务的 `cmd` 和 `internal/app/app.go`；
6. `internal/server/grpc.go`；
7. Handler → Service → Repository → Model；
8. Forwarder → ClientManager → Consul；
9. Middleware、Trace、错误和优雅关闭；
10. `docs/2026-11-11_服务部署与Keycloak配置指南.md`。

不要从生成的 `*.pb.go` 开始阅读。只有需要确认生成接口签名时才进入生成文件，协议定义应回到 `.proto` 查看。

## 18. 当前需要注意的结构问题

- LLM 仍是 Mock 阶段，真实 Provider 和持久化未闭环；
- LLM 的服务名、Consul 注册名和调用方名称需要在正式联调前统一；
- LLM 尚未加入内部 mTLS，当前存在明文例外；
- Web3 的 TRONSCAN 与 TronGrid API Key 当前尚未拆分；
- User 的 Redis、RabbitMQ、本地限流默认关闭，不能把配置预留当作已启用能力；
- Admin 的 Keycloak Management 默认关闭，只创建 PostgreSQL 记录不能保证管理员可登录；
- 公开 Web3 接口必须持续接受匿名限流、预算控制和滥用测试；
- 服务数量增加后，应抽取共享的 gRPC Client、错误、日志和可观测性库，但在接口稳定前不要过早合并领域代码。
