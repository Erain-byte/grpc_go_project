# 生产服务器上传部署与域名切换清单

本文用于把当前 Windows 本地开发环境迁移到 Linux 服务器，并完成 HTTPS 域名、Keycloak、前端和内部服务配置切换。

> 当前仓库还没有 Gateway、Admin、User、Web3、LLM 的统一生产 Dockerfile 和总 Compose。基础设施已有独立 Compose，但还不能直接在服务器执行一次 `docker compose up` 完成全部部署。正式上传前应先补齐应用镜像与生产编排。

## 1. 推荐域名规划

以下使用 `example.com` 占位，实际部署时统一替换：

| 用途 | 示例域名 | 对外后端 |
|---|---|---|
| 用户网页 | `app.example.com` | Expo Web 静态文件 |
| 管理网页及管理 BFF | `admin.example.com` | Vue 静态文件；`/admin/*`、`/oauth2/*` 转发 OAuth2 Proxy |
| 公共 API | `api.example.com` | Gateway `9080` |
| 统一身份认证 | `auth.example.com` | Keycloak `8180` |

公网只开放 `80/443`。Consul、PostgreSQL、Redis、RabbitMQ、Jaeger、pprof、Keycloak `8180/9000`、各服务 gRPC 端口不得直接暴露公网。

## 2. 需要上传的内容

上传到服务器，例如 `/opt/grpc-go`：

- 各服务源码或 CI 构建出的镜像；
- `deploy/` 中生产所需的 Compose、Nginx 示例和初始化文件；
- Gateway、Admin、User、Web3、LLM 的生产 YAML；
- Proto 依赖对应的稳定版本；
- 前端构建产物；
- 数据库迁移程序；
- 不含真实密钥的部署文档。

不得上传到 Git 或普通制品目录：

- `.env` 真实密码；
- mTLS 私钥；
- Keycloak Client Secret；
- TRON、模型供应商等 API Key；
- 数据库备份与用户数据。

建议服务器目录：

```text
/opt/grpc-go/
├── compose/
├── config/
│   ├── gateway.yaml
│   ├── admin.yaml
│   ├── user.yaml
│   ├── web3.yaml
│   └── llm.yaml
├── env/
│   └── production.env
├── secrets/
│   └── mtls/
│       ├── ca/ca.crt
│       ├── gateway/service.crt + service.key
│       ├── admin/service.crt + service.key
│       ├── user/service.crt + service.key
│       ├── web3/service.crt + service.key
│       └── llm/service.crt + service.key
└── logs/

/var/www/grpc-go/
├── user/
└── admin/
```

目录权限建议：私钥 `0600`，Secret 目录仅容器运行用户可读，配置文件只读挂载。

## 3. DNS 与 HTTPS

在域名服务商添加四个 `A`/`AAAA` 记录，全部指向服务器公网 IP：

```text
app.example.com
admin.example.com
api.example.com
auth.example.com
```

先确认 DNS 生效，再通过 Certbot 或云厂商证书签发 HTTPS 证书。参考配置：

- `deploy/production/nginx/grpc-go.conf.example`

公网 HTTPS 证书由 Nginx 使用；内部 gRPC mTLS 证书由 Gateway/Admin/User/Web3/LLM 使用。两套证书用途不同，不能混为一套。

## 4. 前端生产构建

用户端构建前注入：

```dotenv
EXPO_PUBLIC_KEYCLOAK_ISSUER=https://auth.example.com/realms/grpc-project
EXPO_PUBLIC_KEYCLOAK_CLIENT_ID=user-app
EXPO_PUBLIC_GATEWAY_URL=https://api.example.com
```

构建：

```bash
cd frontend/user
npm ci
npx expo export --platform web
```

将 `dist/` 上传到 `/var/www/grpc-go/user/`。

管理端构建前注入：

```dotenv
VITE_ADMIN_BFF_URL=https://admin.example.com
```

构建：

```bash
cd frontend/admin
npm ci
npm run build
```

将 `dist/` 上传到 `/var/www/grpc-go/admin/`。

`EXPO_PUBLIC_*` 与 `VITE_*` 会写入浏览器代码，只能放公开 URL 和公开 Client ID，不能放 Secret。

## 5. Keycloak 生产修改

### 5.1 Keycloak 容器

使用 `deploy/identity/compose.prod.yaml`，至少设置：

```dotenv
KEYCLOAK_HOSTNAME=auth.example.com
KEYCLOAK_DB_PASSWORD=...
KEYCLOAK_BOOTSTRAP_ADMIN_USERNAME=...
KEYCLOAK_BOOTSTRAP_ADMIN_PASSWORD=...
USER_WEB_CLIENT_SECRET=...
ADMIN_WEB_CLIENT_SECRET=...
```

生产必须使用 `start`，不能使用 `start-dev`。Nginx 终止 TLS，因此 Keycloak 保持：

```yaml
KC_HOSTNAME: https://auth.example.com
KC_HOSTNAME_STRICT: "true"
KC_HTTP_ENABLED: "true"
KC_PROXY_HEADERS: xforwarded
```

上线后 discovery 中必须返回：

```text
issuer = https://auth.example.com/realms/grpc-project
```

### 5.2 `user-app` 公共客户端

保持 Public Client、Authorization Code、PKCE `S256`，修改为：

```text
Valid redirect URIs:
https://app.example.com/oauth/callback
web3-user://oauth/callback

Valid post logout redirect URIs:
https://app.example.com/*
web3-user://*

Web origins:
https://app.example.com
```

### 5.3 `admin-web` 机密客户端

```text
Valid redirect URIs:
https://admin.example.com/oauth2/callback

Valid post logout redirect URIs:
https://admin.example.com/*

Web origins:
https://admin.example.com
```

Client Secret 必须与 OAuth2 Proxy 中的 `ADMIN_WEB_CLIENT_SECRET` 一致。

### 5.4 其他 Keycloak 项目

- `grpc-api-audience` 继续作为默认 Client Scope，Access Token 的 `aud` 必须包含 `grpc-api`；
- Realm roles 保留 `user`、`admin`、`super-admin`；
- `admin-management` 若启用，使用独立 Service Account 和最小权限；
- 删除或禁用临时管理员，创建永久管理员并启用 MFA；
- Realm 导入文件只会初始化不存在的 Realm，不应依赖它覆盖已经存在的生产配置。

## 6. OAuth2 Proxy 生产修改

Admin Proxy 至少修改为：

```text
OAUTH2_PROXY_COOKIE_SECURE=true
OAUTH2_PROXY_REDIRECT_URL=https://admin.example.com/oauth2/callback
OAUTH2_PROXY_OIDC_ISSUER_URL=https://auth.example.com/realms/grpc-project
OAUTH2_PROXY_LOGIN_URL=https://auth.example.com/realms/grpc-project/protocol/openid-connect/auth
OAUTH2_PROXY_WHITELIST_DOMAINS=admin.example.com
OAUTH2_PROXY_UPSTREAMS=http://gateway:9080
```

容器在同一网络时，Token/JWKS 内部请求可以走 `http://keycloak:8080`；浏览器登录地址和 Token 的 `iss` 必须始终使用公网 HTTPS 域名。

当前用户 Expo Web 直接采用 OIDC Authorization Code + PKCE，并直接调用 Gateway，因此 `user-oauth2-proxy` 不是用户网页上线的必需组件。若保留该代理，应单独分配入口并同步 Keycloak 回调地址，不能继续使用 localhost。

## 7. 各服务生产 YAML 修改

### 7.1 所有服务共同修改

- `environment` 改为 `production`；
- 服务监听地址改为 `0.0.0.0`；
- `advertise_host` 使用容器 DNS 名或可达内网地址，不能使用 `127.0.0.1`；
- PostgreSQL、Redis、RabbitMQ、Consul、Jaeger 地址使用 Compose 服务名；
- `issuer` 必须精确等于 `https://auth.example.com/realms/grpc-project`；
- `jwks_url` 可使用同一公网地址；若容器 DNS 与证书策略明确，也可用内部 Keycloak JWKS 地址；
- Windows 的 `D:/grpc_go_project/...` 全部换成容器内只读挂载路径；
- pprof 不对公网开放，建议仅监听容器内部管理网络；
-日志写 stdout 更适合容器收集；如果仍写文件，必须挂载持久卷并配置轮转。

推荐容器内 mTLS 固定路径：

```text
/run/mtls/ca/ca.crt
/run/mtls/service/tls.crt
/run/mtls/service/tls.key
```

证书 SAN、Consul 服务名和 `tls_server_name` 保持一致：

```text
gateway-service
admin-service
user-service
web3-service
llm-service
```

### 7.2 Gateway

```yaml
environment: production
host: "0.0.0.0"
advertise_host: "gateway"

auth:
  access_token:
    issuers:
      - "https://auth.example.com/realms/grpc-project"
    jwks_url: "https://auth.example.com/realms/grpc-project/protocol/openid-connect/certs"

redis:
  host: "redis"

consul:
  host: "consul"
  check_host: "gateway"

grpc_server:
  cert_file: "/run/mtls/service/tls.crt"
  key_file: "/run/mtls/service/tls.key"
  client_ca_file: "/run/mtls/ca/ca.crt"

grpc:
  cert_file: "/run/mtls/service/tls.crt"
  key_file: "/run/mtls/service/tls.key"
  ca_file: "/run/mtls/ca/ca.crt"

tracing:
  endpoint: "jaeger:4317"
```

Consul KV `grpc-go/config/gateway/runtime` 的 CORS 修改为：

```json
{
  "cors": {
    "allow_origins": [
      "https://app.example.com",
      "https://admin.example.com"
    ]
  }
}
```

保留原 KV 中其他限流、熔断和防重放字段，不要只上传这个不完整片段。

### 7.3 Admin

- `host: 0.0.0.0`；
- `database.host: admin-postgres`、容器端口 `5432`；
- `redis.host: redis`；
- `rabbitmq.host: rabbitmq`；
- `consul.host/check_host: consul/admin`；
- `auth.management.base_url` 使用 Keycloak 内部地址 `http://keycloak:8080`；
- Issuer 仍使用公网 `https://auth.example.com/realms/grpc-project`；
- mTLS 路径改为 `/run/mtls/...`；
- tracing 改为 `jaeger:4317`。

### 7.4 User

- `database.host: user-postgres`、端口 `5432`；
- Redis/RabbitMQ/Consul/Jaeger 改为容器服务名；
- `advertise_host/check_host: user`；
- 每个并行实例通过 `USER_SNOWFLAKE_NODE_ID` 使用不同节点号；
- Issuer、JWKS 和 mTLS 路径按共同规则修改。

### 7.5 Web3

- `database.host: web3-postgres`、端口 `5432`；
- Redis/RabbitMQ/Consul/Jaeger 改为容器服务名；
- `advertise_host/check_host: web3`；
- `wallet_signature.domain` 改为正式产品域名；
- `wallet_signature.uri` 改为正式 HTTPS URL；
- `WEB3_TRON_API_KEY` 等上游密钥只通过 Secret 注入；
- 未准备好真实上游密钥和预算保护前，保持 `tron_approvals.enabled: false`。

### 7.6 LLM

- `environment: production`；
- `advertise_host: llm`；
- `consul.address: consul:8500`；
- `tracing.endpoint: jaeger:4317`；
- Issuer/JWKS 改为生产 Keycloak；
- 正式上线前完成 LLM gRPC mTLS，并从其他服务的 `plaintext_services` 删除 `llm-service`；
- 修正服务发现命名：调用方使用 `llm-service`，当前配置注册的是 `llm-service-grpc`，上线前必须统一。

```text
GATEWAY_ENVIRONMENT

GATEWAY_ANTI_REPLAY_SECRET

ADMIN_ENVIRONMENT
ADMIN_DB_PASSWORD
ADMIN_REDIS_PASSWORD

ADMIN_KEYCLOAK_CLIENT_SECRET

USER_ENVIRONMENT
USER_DB_PASSWORD
USER_REDIS_PASSWORD
USER_RABBITMQ_PASSWORD
USER_CONSUL_TOKEN
USER_SNOWFLAKE_NODE_ID

WEB3_ENVIRONMENT
WEB3_DB_PASSWORD
```

域名、主机地址和证书路径目前主要来自 YAML，并不能全部通过环境变量覆盖。因此应为生产环境准备独立 YAML，而不是只修改 `.env`。

## 9. 推荐启动顺序

1. 创建 Docker 网络和持久卷；
2. 启动 PostgreSQL、Redis、RabbitMQ；
3. 启动 Consul、Jaeger；
4. 启动 Keycloak，完成 Realm/Client 核查；
5. 执行 Admin/User/Web3/LLM 数据库迁移；
6. 启动 Web3、LLM；
7. 启动 User、Admin；
8. 启动 Gateway；
9. 启动 Admin OAuth2 Proxy；
10. 部署用户端、管理端静态文件；
11. 启动或重载 Nginx；
12. 执行冒烟测试和链路追踪检查。

## 10. 上线验证

必须验证：

```text
https://auth.example.com/realms/grpc-project/.well-known/openid-configuration
https://app.example.com
https://admin.example.com
https://api.example.com/health
```

并检查：

- 用户 Web 登录、刷新 Token、退出；
- Admin 登录、角色限制、退出；
- Gateway 到 Admin/User/Web3 的 mTLS；
- Access Token 的 `iss`、`aud`、过期时间；
- Consul 中实例地址不是 `127.0.0.1`；
- Jaeger 能看到 `Gateway → User/Admin → Web3/LLM`；
- 数据库迁移版本正确；
- Redis/RabbitMQ/PostgreSQL/pprof/Jaeger UI 没有公网暴露；
- 服务器重启后容器、数据卷和证书仍正常。
